Operating Systems

What actually happens inside a Linux box. PE interviewers love "what happens when…" questions that walk from a shell command down through the kernel. Build the mental model here; the Linux page turns it into debugging skill.

The big picture: kernel vs user space basics

A program never touches hardware. It asks the kernel via system calls — the only doorway. printf → libc buffers → write(1, buf, n) syscall → kernel → tty driver. Use strace to see every syscall a process makes; this is the PE's X-ray.

Processes basics

A process is a running program: its own virtual address space, file descriptors, credentials, signal handlers, and at least one thread. Tracked by the kernel in a task_struct; identified by a PID; has a parent (PPID). Everything descends from PID 1 (init/systemd).

fork, exec, wait: how every program starts deep dive

Copy-on-write: fork doesn't copy memory; it copies page tables and marks pages read-only. The first write by either process triggers a page fault and the kernel copies that page. This makes fork cheap and is why Redis can snapshot by forking. vfork/posix_spawn exist for the fork-then-immediately-exec case.

Daemonizing (old-school): fork, parent exits (child is orphaned → adopted by init), setsid() for a new session (no controlling terminal), fork again, chdir /, close FDs 0–2, redirect to /dev/null. systemd makes this unnecessary — it runs services in the foreground and manages them.

Threads & concurrency basics

Process

Own address space. Isolation: a crash doesn't take down others. Communication needs IPC. Creation ~100 µs+ (fork COW). Context switch flushes TLB (expensive).

Thread

Shares address space, heap, FDs with sibling threads; own stack, registers, PC. Cheap communication (shared memory) but data races. Linux implements threads as tasks sharing resources (clone() with CLONE_VM|CLONE_FILES…); each has its own TID; ps -L shows them.

Synchronization primitives

  • Mutex: one owner at a time; others block (futex: fast user-space path, kernel only on contention).
  • Spinlock: busy-wait; for very short critical sections, kernel/multi-core only.
  • RW lock: many readers or one writer.
  • Semaphore: counter; N concurrent holders.
  • Condition variable: wait for a predicate, signaled by another thread; always paired with a mutex and a while-loop (spurious wakeups).
  • Atomics / CAS: lock-free counters, compare-and-swap loops.

Deadlock

Four necessary conditions (Coffman): mutual exclusion, hold and wait, no preemption, circular wait. Break one to prevent: acquire locks in a global order (kills circular wait), try-lock with timeout + back off, or acquire all at once. Detect via wait-for graph cycles. Related: livelock (everyone backs off forever), starvation, priority inversion (low-priority holder blocks high-priority waiter; fixed by priority inheritance — the Mars Pathfinder bug).

Python's GIL (common PE question)

CPython's Global Interpreter Lock lets only one thread execute Python bytecode at a time → threads don't speed up CPU-bound code (use multiprocessing), but do help I/O-bound code (the GIL is released during blocking I/O). asyncio: single-threaded cooperative concurrency via an event loop — ideal for many concurrent network connections.

CPU scheduling deep dive

The scheduler decides which runnable task gets each CPU core and for how long. Linux's CFS (Completely Fair Scheduler; replaced by EEVDF in 6.6) tracks each task's virtual runtime and always runs the one that has had the least CPU, weighted by nice (−20 highest priority … +19 lowest). Tasks sit in a red-black tree ordered by vruntime. Time slices are dynamic (~1–6 ms); a sleeping task that wakes gets scheduled soon because its vruntime is low (good for interactive/I/O-bound).

  • Context switch: save registers/PC/stack pointer, switch page tables (CR3; flushes TLB unless PCID), restore the next task. ~1–5 µs direct cost + cache/TLB pollution. vmstat cs column; very high = too many threads or lock thrashing.
  • Preemptive (kernel interrupts a running task on timer tick / wakeup) vs cooperative (task yields — e.g., goroutines before Go 1.14, asyncio).
  • Real-time classes: SCHED_FIFO / SCHED_RR run before all normal tasks — dangerous if a busy loop (can lock up a core).
  • CPU affinity (taskset), NUMA: memory attached to a remote socket is slower; the scheduler tries to keep tasks near their memory.
  • cgroups CPU controller: shares (relative weight) and quota (hard cap: cpu.max) — how containers get "2 CPUs". Throttling shows up as latency spikes while CPU looks idle! Check cpu.stat nr_throttled.
Load average explained (asked constantly)The 1/5/15-minute exponentially-damped averages of the number of tasks that are running or runnable (R) plus in uninterruptible sleep (D). On a 4-core box, load 4 ≈ fully busy; load 8 = tasks waiting. Because of D, a high load with idle CPU means an I/O bottleneck (disk, NFS) — look at vmstat b column, iostat %util/await, ps -eo stat for D. Load average alone never tells you why — it's a prompt to look at CPU vs I/O.

Memory: virtual memory & paging basics

Every process sees a private, contiguous, huge address space (48 bits = 256 TB) — an illusion. The MMU translates virtual addresses to physical via page tables (4 KB pages, 4-level tree on x86-64), cached in the TLB. The kernel lazily backs pages with physical RAM only when touched.

Page faults

  • Minor (soft) fault: page not mapped but in RAM (first touch of allocated memory, COW, page cache hit) — microseconds. Normal.
  • Major (hard) fault: page must be read from disk (swap-in, or file-backed page not in cache) — milliseconds. High major fault rate (sar -B, vmstat si/so) = memory pressure → thrashing.
  • Segfault: accessing an unmapped or protected page → SIGSEGV.

Where memory goes (free -m is misleading)

total used free shared buff/cache available Mem: 64000 21000 2000 300 41000 42000 ▲ ▲ ▲ "free" is tiny — GOOD page cache: file data what you can actually allocate unused RAM is wasted RAM kernel evicts it on demand (free + reclaimable cache)
  • Page cache: kernel caches file contents in otherwise-idle RAM; reads hit RAM, writes become dirty pages flushed by background writeback (every ~30 s or when dirty ratio exceeded). This is why the second read of a file is instant and why sync exists.
  • RSS (resident set), VSZ (virtual size — meaningless for leaks), PSS (proportional, splits shared), USS (unique). Leak hunting: watch RSS/USS over time.
  • Anonymous memory (heap/stack; only reclaimable to swap) vs file-backed (reclaimable by dropping).
  • Huge pages (2 MB): fewer TLB misses for big-memory apps (DBs). Transparent huge pages can cause latency spikes (compaction) — DBs often disable them.
  • Overcommit: Linux lets you malloc more than exists (vm.overcommit_memory); the bill comes due on touch → OOM.

The OOM killer PE

When RAM + swap are exhausted and nothing is reclaimable, the kernel picks a process to kill based on oom_score (mostly RSS; tunable with oom_score_adj −1000…1000). Log in dmesg: Out of memory: Killed process 1234 (java) total-vm:… anon-rss:…. In cgroups (containers), the container's limit triggers a cgroup OOM, killing a process inside — Kubernetes reports OOMKilled, exit code 137. Debug: dmesg -T | grep -i oom, cgroup memory.events, check for a leak (RSS growth) vs undersized limit vs page-cache-counted-against-cgroup confusion.

Swap: friend or foe?

Swap lets the kernel move rarely-used anonymous pages to disk to keep more page cache. A little swapping of cold pages is fine; sustained swapping (si/so in vmstat) means thrashing — latency goes 1000×. Many fleets run swapless so failure is a fast, clean OOM instead of slow death; others use small swap + vm.swappiness tuning. Know both arguments.

Files, file descriptors & the VFS basics

"Everything is a file": regular files, directories, devices, pipes, sockets are all accessed via file descriptors — small integers indexing the process's FD table → open file description (offset, flags) → inode. FD 0 = stdin, 1 = stdout, 2 = stderr.

process FD table open file table (system-wide) inode (per file on disk) ┌───┬────────┐ ┌────────────────────────┐ ┌──────────────────────┐ │ 0 │ ───────┼─────────► │ /dev/pts/3 off=0 RDWR │ │ ino 48213, mode 0644 │ │ 1 │ ───────┼──┐ ├────────────────────────┤ │ uid, gid, size, times│ │ 2 │ ───────┼──┴──────► │ /dev/pts/3 (shared) │ │ link count = 1 │ │ 3 │ ───────┼─────────► │ /var/log/app.log ├────────► │ block pointers ──► data blocks │ 4 │ ───────┼─────────► │ socket TCP :443 │ └──────────────────────┘ └───┴────────┘ └────────────────────────┘ fork() copies the FD table → child shares the SAME open file descriptions (shared offset!) — why redirected output from parent+child interleaves correctly.
  • Inode stores metadata + where data blocks are — not the filename. The directory is a file mapping names → inode numbers. Hard link = another name for the same inode (link count++); symlink = a file containing a path. Deleting a file = unlink: remove the name, decrement count; data freed only when count = 0 and no process has it open.
  • Classic incident: disk full but du shows space free → a process still holds a deleted log file open. lsof +L1 or lsof | grep deleted; truncate via /proc/PID/fd/N or restart the process. Also: out of inodes (df -i) from millions of tiny files while bytes remain.
  • Permissions: rwx for owner/group/other, octal (755), setuid/setgid/sticky bits; directory x = traverse. umask masks defaults.
  • FD limits: per-process (ulimit -n, default 1024!) and system-wide (fs.file-max). "Too many open files" (EMFILE) is a classic outage for servers with many connections; raise in systemd unit LimitNOFILE.
  • Write path: write() copies into page cache (returns immediately) → marked dirty → writeback to disk later. Durability requires fsync() (file data + metadata) — DBs call it on commit. Power loss between write and fsync loses data. O_DIRECT bypasses cache.
  • VFS abstracts filesystems (ext4, XFS, btrfs, tmpfs, procfs, NFS, overlayfs for containers) behind one API. Journaling (ext4/XFS) logs metadata changes before applying → consistent after crash without full fsck.
  • mmap: map a file into memory; reads become page faults; shared between processes → the basis of shared libraries and some DBs.

I/O models: blocking, non-blocking, epoll, io_uring deep dive

How does one server handle 100k connections (the "C10k" problem)?

read() blocks until data arrives. One thread per connection: simple, but 100k threads = 100k stacks (8 MB virtual each), heavy context switching. Apache prefork/worker, classic Java servlets.

Set sockets O_NONBLOCK; ask the kernel "which of these FDs are ready?" select/poll are O(n) per call; epoll (Linux) registers interest once and returns only ready FDs in O(1) — scales to millions. One thread runs an event loop: wait → handle ready events (never block) → repeat. nginx, Node.js, Redis, HAProxy, Go's netpoller, Python asyncio all do this. Level-triggered vs edge-triggered modes. Multi-core: one event loop per core (nginx workers, SO_REUSEPORT).

Submit operations to a ring buffer shared with the kernel; kernel completes them asynchronously and posts completions — no syscall per operation, works for files too (epoll doesn't help with regular file reads, which always "block"). The modern high-performance path.

Zero-copy: sendfile() moves file → socket inside the kernel (no user-space copy); Kafka and nginx use it for huge throughput.

Boot process: power on → login basics

Firmware (BIOS/UEFI): POST, hardware init, finds the boot device, loads the bootloader (from MBR or the EFI System Partition).
Bootloader (GRUB): presents menu, loads the kernel image (vmlinuz) and initramfs into memory, passes kernel command line (root=…, quiet).
Kernel: decompresses, initializes CPUs, memory, drivers; mounts initramfs as a temporary root; runs its /init which loads modules needed for the real root (storage, LVM, crypto, network for PXE/NFS root), then switch_root to the real filesystem.
PID 1 — systemd: reads unit files, builds the dependency graph, reaches the default target (multi-user/graphical) by starting units in parallel: mounts (/etc/fstab), network, logging (journald), sshd, your services.
Login: getty on TTYs / display manager; sshd accepts connections; PAM authenticates; shell starts.

Debug boot: dmesg (kernel ring buffer), journalctl -b, systemd-analyze blame. Datacenter servers often PXE boot: NIC gets DHCP → TFTP downloads a bootloader → fetches kernel+initramfs over HTTP → installer or diskless image. Know this flow for "how would you provision 10k servers".

Containers: namespaces & cgroups deep dive

A container is just a normal Linux process with a restricted view and limited resources — no hypervisor.

Namespaces (isolation — what you can see)

  • pid: own PID 1; can't see host processes
  • net: own interfaces, routes, iptables; veth pair bridges to host
  • mnt: own mount table / root filesystem (overlayfs image layers)
  • uts: own hostname
  • ipc, user (uid 0 inside = unprivileged outside), cgroup, time

cgroups (limits — what you can use)

  • cpu: weight & quota (throttling)
  • memory: limit → OOM inside the group
  • io: bandwidth/IOPS limits
  • pids: max processes (fork bomb protection)
  • Hierarchy under /sys/fs/cgroup/; systemd puts every service in its own cgroup — systemd-cgtop

Plus: capabilities (split root into ~40 privileges, e.g., CAP_NET_BIND_SERVICE), seccomp (syscall filter), overlayfs (copy-on-write layered image). VMs vs containers: VMs virtualize hardware (own kernel; stronger isolation; heavier); containers share the kernel (fast start, dense, kernel bug = shared risk). gVisor/Firecracker blend the two.

Self-test: OS rapid fire

What's the difference between a process and a thread, at the kernel level in Linux?
Both are tasks (task_struct) created with clone(). A thread is a task created with flags that share the address space (CLONE_VM), FDs (CLONE_FILES), signal handlers, etc. with its creator; a process gets copies (COW). Threads share a thread-group ID (the PID you see); each has its own TID, stack, registers.
Load average is 30 on an 8-core box but CPU is 90% idle. What's going on?
Tasks in uninterruptible (D) sleep count toward load. Likely an I/O bottleneck: disk saturated, or a hung NFS mount. Check vmstat 1 (b column, wa%), iostat -x 1 (await, %util), ps -eo pid,stat,wchan,cmd | awk '$2 ~ /D/'.
A disk is 100% full, you delete a 50 GB log, but df still says 100%. Why?
A process still holds the file open; unlink removed the name but the inode and blocks stay until the last FD closes. Find it with lsof +L1; truncate via : > /proc/PID/fd/N or restart/HUP the process. Prevention: logrotate with copytruncate or signal the app to reopen logs.
Why can't you kill -9 a process?
Either it's in D state (uninterruptible I/O wait — the signal is delivered when the syscall returns, which may be never if the storage is hung) or it's a zombie (already dead; nothing to kill — reap by fixing/killing the parent). Also possible: PID 1 in a container ignores signals it has no handler for.
What happens when a process calls malloc(1 GB) and never touches it?
glibc uses mmap for large allocations → the kernel just reserves virtual address range (VSZ grows); no physical pages are assigned (RSS unchanged) until pages are touched (minor faults). With overcommit, even allocating more than physical RAM succeeds.
Explain copy-on-write and one system that relies on it.
After fork, parent and child share physical pages marked read-only; a write triggers a page fault and the kernel copies just that page. Redis BGSAVE forks and the child writes the snapshot while the parent keeps serving — memory only grows by the pages modified during the save.
What is the difference between SIGTERM and SIGKILL, and how should a service handle shutdown?
SIGTERM is catchable: stop accepting new work, finish in-flight requests, flush, close, exit (graceful). SIGKILL is uncatchable, immediate — no cleanup; data in process memory is lost. Orchestrators send TERM, wait a grace period (30 s), then KILL.
How does epoll let one thread serve 100k connections?
Sockets are non-blocking; the thread registers them with epoll once; epoll_wait returns only the FDs that are ready (O(ready), not O(n)). The event loop processes each ready socket without blocking and goes back to waiting; idle connections cost only memory, not threads.
Memory in a container keeps hitting its limit though the app's heap is small. Why?
cgroup memory accounting includes page cache (file reads/writes by the container) and kernel memory, not just anonymous RSS. Check memory.stat (file vs anon). Cache is reclaimable so it rarely causes OOM, but it inflates usage graphs; if OOM does happen, it's anon memory — look for leaks or set a realistic limit.
