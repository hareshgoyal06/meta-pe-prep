System Design Case Studies

Each walkthrough follows the same 5-step framework you'll use in the interview: Requirements → Estimation → High-level design → Deep dives → Failure modes & operations. Infra-flavored cases (metrics, logs, config, deploys, scheduler) are marked PE — expect those at Meta.

The framework (memorize)
  1. Clarify requirements (3–5 min): functional (what it does), non-functional (scale, latency, consistency, availability, durability), out of scope. Ask about read/write ratio, data size, geographic distribution.
  2. Estimate (3 min): QPS, storage, bandwidth, memory. Say the implications out loud ("so one DB won't do").
  3. High-level design (10 min): boxes & arrows, API, data model/schema. Get a working system end to end before optimizing.
  4. Deep dive (15 min): the 2–3 hardest parts; the interviewer will steer. Trade-offs at every choice.
  5. Wrap up (5 min): bottlenecks, failure modes, monitoring, how you'd scale 10×, what you'd do differently.

URL shortener (TinyURL)

Requirements

Functional: create short URL for a long URL; redirect; optional custom alias & expiry. Non-functional: very low redirect latency, high availability (redirects must always work), read-heavy (100:1), links must not collide.

Estimation

100M new URLs/month ≈ 40 writes/s; 100:1 → 4k reads/s (peak ~10k). Each record ~500 B → 50 GB/month → 3 TB over 5 years. Easily fits one DB with replicas; cache the hot 20%.

Design

Client ──► LB ──► API servers (stateless) ──► Cache (Redis: short→long) ──► DB (short_code PK, long_url, user, created, expires) │ └──► ID generator (for new codes)

API: POST /shorten {long_url, alias?, ttl?} → {short}; GET /{short} → 301/302 Location: long_url.

Deep dives

Generating the short code

7 chars of base62 = 62⁷ ≈ 3.5 trillion codes. Options: (a) hash MD5/SHA of the long URL, take first 7 chars — collisions possible, must check & re-salt; same URL → same code (dedupe bonus). (b) Counter → base62: a global counter (ZooKeeper-assigned ranges per server, or Snowflake IDs) encoded to base62 — no collisions, but sequential codes are guessable (add a shuffle or random offset). (c) Pre-generated key service: a service pre-fills a table of unused random keys; API servers grab batches. Recommended: (b) or (c).

301 vs 302

301 (permanent): browser caches, never asks again → less load, but you lose analytics and can't change the target. 302 (temporary): every click hits you → analytics, updatable. Most shorteners use 302 for analytics.

Scaling & failures

Reads: cache-aside with LRU; cache hit ratio ~90%+ since clicks follow a power law. DB: hash-partition by short code when > 1 node; replicas for HA. Rate-limit creation per user/IP to prevent abuse. Expiry: lazy delete on read + background sweeper. Monitoring: redirect p99 latency, 404 rate, cache hit ratio, DB replication lag, create API error rate.

Distributed rate limiter PE

Requirements: limit requests per client (user/IP/API key) to N per window; low latency overhead (<1 ms); accurate-ish across many API servers; highly available (fail open or closed? — decide: usually fail open for user-facing, closed for abuse-protection).

Client ──► API Gateway ──┬─► rate limiter middleware ──► Redis cluster (counters / token buckets, keyed by client id, sharded by key) │ │ allow → forward to service │ └ deny → 429 + Retry-After + X-RateLimit-Remaining └─► Rules service (limits per tier, cached in memory, pushed on change)
Algorithm choice & atomicity

Token bucket (burst + steady rate) or sliding-window counter. In Redis, make check-and-decrement atomic with a Lua script or MULTI; store {tokens, last_refill} per key with TTL. Sliding window: INCR key:minute + EXPIRE, weight previous window by overlap.

Distributed accuracy

Centralized Redis = exact but adds a network hop and is a dependency. Alternative: each gateway node keeps local counters and syncs to Redis asynchronously every 100 ms — slight over-admission, near-zero latency, survives Redis outage. Or route the same client to the same gateway node (consistent hashing) so counters are local and exact.

Operations

Metrics: allow/deny rate per rule, Redis latency, Redis availability. Fail-open flag. Hot keys (one abusive client) can hammer one Redis shard — replicate hot keys or shard by key+suffix. Rules live in config with gradual rollout.

Metrics & monitoring system (like Prometheus / Meta's ODS) PE

This is the most PE-flavored design question and extremely likely. Requirements: collect metrics from 1M hosts, each emitting ~1k time series every 10 s; store 2 weeks raw, 1 year downsampled; query dashboards (p99 latency over last 6 h for service X) in <1 s; alert on rules within 1 min; must be more reliable than what it monitors.

Estimation

1M hosts × 1k series = 1B active series. 1B / 10 s = 100M data points/s. Each point (timestamp + float) 16 B raw → 1.6 GB/s; with Gorilla compression (~1.4 B/point) ≈ 140 MB/s → 12 TB/day → 170 TB for 2 weeks. Way beyond one node: sharded ingestion & storage.

Data model & storage engine

Series = metric name + label set (http_requests_total{service="api",host="h123",status="500"}) → series ID (hash). Points = (ts, value). Store per-series in time-ordered blocks. Gorilla compression: delta-of-delta timestamps (regular intervals → ~1 bit), XOR of consecutive floats (similar values → few bits) → 12× compression. Keep last 26 h in memory (serves 85%+ of queries), flush immutable 2 h blocks to disk/blob, build an inverted index label→series IDs for queries. Downsample older data (1 min, 1 h aggregates: min/max/avg/count/sum) via background jobs.

Sharding & hot spots

Shard by hash(series ID) so a service's series spread out; queries fan out and merge. Alternative: shard by tenant/service for query locality but risk hot shards. Cardinality explosion (a label with user IDs) is the classic failure — enforce limits per metric at ingest, alert on series count growth.

Alerting

Rules evaluated every 10–60 s against the query layer: rate(errors[5m])/rate(requests[5m]) > 0.01 for 5m. "for" duration avoids flapping. Alerts → Alertmanager: dedupe, group, silence, route to pager/Slack. Alert evaluator must be replicated (2 evaluators, dedupe) — monitoring that goes down with the outage is useless. Run it in a different failure domain from the systems it monitors; have a dead-man's-switch (an alert that always fires; if it stops, monitoring is broken).

Reliability

Agents buffer locally during ingest outages (bounded, drop oldest). Kafka decouples ingest from storage so storage restarts don't lose data. Replicate each TSDB shard 2–3× (ingest writes to all, queries pick any). Ingest is at-least-once → storage dedupes by (series, ts). Prefer availability over consistency: a slightly late/missing point is fine; a down dashboard during an incident is not. Degraded mode: serve from any replica, allow partial query results with a warning.

Log aggregation pipeline (ELK / Scribe → Scuba) PE

Requirements: collect logs from 100k hosts (1 TB/day… or 1 PB/day at Meta scale), search by service/host/time/text within seconds for the last 7 days, retain 30–90 days cheaply, never block the application when logging.

app ──stdout/file──► local agent (Fluent Bit / Scribe daemon: tail, parse, buffer on disk, batch, compress) │ ▼ Kafka (topic per log type, partition by host-hash) ◄── backpressure buffer, 24h retention ├──► Indexer workers ──► Elasticsearch / hot search cluster (sharded by time: daily indices) ├──► Archiver ──► blob storage (compressed Parquet by hour) ──► Presto/Athena for ad-hoc └──► Stream processors (alerts on error patterns, metrics derived from logs)
Key decisions
  • Structured logging (JSON with service, host, level, trace_id) → indexable fields; avoid regex at scale.
  • Time-based indices: easy retention (drop old index), queries hit only relevant days. Hot/warm/cold tiers: SSD → HDD → blob.
  • Sampling: keep 100% of errors, sample debug/info at 1–10% under load; dynamic sampling by error rate.
  • Agent must never block the app: async, bounded disk buffer, drop with a counter when full; the dropped-count is itself a metric.
  • Security: PII scrubbing at the agent; access control per index.
Failure modes

Indexer slower than ingest → Kafka lag grows (alert on lag), scale indexers; ES cluster red (shard unassigned) → queries fail: replicate shards, cap shards per node; a single host logging in a loop floods the pipeline → per-host rate limits at agent; disk full on agent host → bounded buffer. Monitor: ingest rate, end-to-end delay (log timestamp vs index time), drop counts, query latency.

Configuration distribution / feature flags PE

Requirements: push a config change (e.g., a feature flag, a rate-limit value, a kill switch) to 1M hosts within seconds; versioned with rollback; gradual rollout (1% → 100%); hosts must start and run even if the config service is down; audit who changed what.

Engineer ──► Config UI/CLI ──► Config service (validate schema, store versioned in Git/DB, canary %) ──► Pub/sub "config changed v123" │ │ ▼ ▼ Distribution tier (regional caches / CDN-like, serve by version) ──► host agent (long-poll or watch) │ writes /etc/config/app.json atomically (write tmp + rename) │ keeps last-known-good on disk ▼ application (inotify / periodic reload / SIGHUP)
Why this is hard
  • Thundering herd: 1M hosts fetching simultaneously after a change → regional caches, jitter, serve immutable versions by content hash so caches/CDN work.
  • Bad config = outage (Facebook 2021, Cloudflare 2019 regex). Validate schema, dry-run, canary to a small % and auto-rollback on SLO regression. Treat config like code: review, versioning, instant revert.
  • Bootstrapping: hosts must boot without the service — bake a default + last-known-good on disk.
  • Consistency: all hosts won't see v123 at the same instant; design features to tolerate mixed versions for a few seconds (or coordinate via epochs if needed).
  • Watch vs poll: ZooKeeper/etcd watches for small fleets; for millions, long-poll to a distribution tier with ETags.

Deployment system (push code to 100k hosts) PE

Requirements: deploy a new binary/container to a service's fleet with zero downtime; staged rollout with automatic health gates; fast rollback; parallelism limits so capacity never drops below N−1; auditable.

CI builds artifact v42 ──► artifact store (blob, content-addressed, replicated per region; P2P/BitTorrent-style distribution for large fleets) │ ▼ Deploy orchestrator (state machine per rollout: canary 1% → 10% → 50% → 100%, per-region/per-failure-domain ordering) │ for each batch (≤ 5% of hosts, never two from the same shard/rack): │ 1. drain from LB (fail health check / deregister), wait for in-flight to finish │ 2. stop old, pull artifact (pre-fetched), start new, run smoke test │ 3. re-register, wait for healthy + bake time (10 min) comparing canary metrics vs baseline │ 4. any SLO regression → halt + auto-rollback (previous artifact still on disk → seconds) ▼ Host agent executes steps, reports status; orchestrator persists state so it survives its own restart
Discussion points
  • Artifact distribution at scale: 1 GB × 100k hosts = 100 TB → regional caches + peer-to-peer (Meta, Uber's Kraken, Facebook's early BitTorrent use).
  • Health gates: not just "process up" — compare error rate/latency of new vs old cohort (canary analysis). Statistical: enough traffic to be meaningful.
  • Schema migrations and backward compatibility across mixed versions.
  • Rollback must be a first-class, tested, one-click action; keep N previous versions on disk.
  • Orchestrator HA: leader-elected, state in a durable store, idempotent steps (a retry after crash must not double-restart).
  • Emergency "break glass" path that skips stages, with audit.

Distributed job scheduler / cron PE

Requirements: run millions of scheduled jobs (cron expressions, one-offs, delayed tasks), each executed at least once (ideally exactly once), on time (±seconds), with retries, dependencies, and visibility; survive scheduler failures.

Job definitions (DB: id, schedule, payload, retry policy, owner) │ Scheduler leaders (sharded by job-id hash; each shard has a Raft/ZK-elected leader) ─ scans "next_run ≤ now" (index on next_run) every second │ enqueue (job_id, run_id, scheduled_ts) ──► Kafka / priority queue (per-priority topics) ▼ Workers (pull, claim run_id with lease in DB → CAS to RUNNING, heartbeat, exec, mark DONE/FAILED, schedule retry with backoff) │ Dead-letter after N failures ──► alerts; UI shows run history, logs, durations
Hard parts
  • Exactly-once execution: leader election avoids double-scheduling; worker claim via compare-and-swap avoids double-run; jobs themselves should be idempotent because leases can expire mid-run (worker GC pause) — fencing token = run_id.
  • Clock skew: use the DB/leader's clock, not workers'. Missed runs after downtime: catch-up policy (run once vs run all missed vs skip).
  • Hot second: many jobs scheduled at :00 → jitter, spread, priority queues.
  • Dependencies (DAGs): Airflow-style; a job's trigger is "all parents DONE".
  • Isolation: a runaway job shouldn't starve others — per-tenant quotas, resource limits (cgroups), timeouts.

News feed (Facebook / Twitter timeline)

Requirements: post → appears in followers' feeds within seconds; feed load p99 < 500 ms; 2B users, 500M DAU, avg 300 friends, celebrities with 100M followers; ranked (not just chronological).

Fan-out on write vs fan-out on read
Fan-out on write (push)Fan-out on read (pull)
PostWrite post_id into each follower's feed cache (300 writes)Just store the post
Read feedRead one precomputed list — fastQuery all followees' recent posts, merge, sort — slow, N queries
Celebrity w/ 100M followers100M writes per post — too slow & wasteful (most are inactive)Fine
Inactive usersWasted workNo waste

Hybrid: push for users with < ~10k followers; pull for celebrities (merge at read time); skip pushing to users inactive > 30 days (rebuild on login). This is what Twitter/Instagram do.

Other dives
  • Feed cache sizing: 500M DAU × 500 ids × 8 B = 2 TB → fine across a Redis cluster.
  • Ranking: candidate posts (ids) → hydrate (posts, authors, counts from caches) → ML score → re-sort → paginate with cursor (not offset).
  • Media: images/video in blob storage + CDN; feed carries URLs.
  • Consistency: eventual is fine; your own post should appear immediately (insert into own feed synchronously).
  • Deletes/privacy: filter at read time (check post still exists & visible) rather than deleting from 100M feeds.

Chat / messaging (WhatsApp, Messenger)

Requirements: 1:1 and group messages, delivered in <100 ms when online, stored for offline delivery, ordering within a conversation, delivery/read receipts, presence, end-to-end encryption (optional), 1B users, 100B messages/day.

Mobile ◄──WebSocket (persistent)──► Chat gateway (stateful: holds connections; 1M conns/box; sharded by user) │ user → gateway mapping in a session store (Redis) ▼ Message service ──► Message store (Cassandra/HBase: partition=conversation_id, cluster by message_id/time) │ ids: Snowflake (time-ordered) per conversation; sequence number per conversation for ordering ├──► look up recipient's gateway → push; if offline → store + push notification (APNs/FCM) via notification service └──► Group: fan out to members (small groups push; huge groups pull from the conversation log) Presence service: heartbeats every 30s → last_seen; subscribe to friends' presence (pub/sub), debounce flapping
Deep dives
  • Why WebSockets: server push without polling; one connection per device. Gateway is stateful — on gateway failure clients reconnect (jittered) and re-sync from last received message id.
  • Ordering: per-conversation sequence numbers assigned by the message service (single writer per conversation via partitioning) — clients sort by seq, detect gaps, request missing.
  • Delivery guarantees: at-least-once with client-side dedupe by message id; receipts are messages too (sent → delivered → read).
  • Storage: write-heavy, read recent → LSM wide-column store partitioned by conversation; TTL/archival for old messages; E2E encryption means server stores ciphertext.
  • Scale: 100B msgs/day ≈ 1.2M/s; each ~100 B → 12 TB/day. Gateways: 1B users, ~30% online → 300M connections / 1M per box = 300+ gateway hosts (+ headroom).

Notification service

Send push (APNs/FCM), SMS, email to users from many internal producers; respect user preferences & rate limits (no more than N/day); dedupe; retry on provider failure; track delivery; 10M+/min bursts (e.g., breaking news).

Producers ──► Notification API (validate, template, check prefs/opt-outs, dedupe key) ──► Kafka (topic per channel, priority topics) ──► Workers per channel (rate-limited per provider; batch for email) ──► Providers (APNs/FCM/Twilio/SES) with circuit breakers & failover to secondary provider ──► Delivery receipts → status store; retries with backoff → DLQ; analytics; user-facing "notification center" store

Key points: idempotency key to avoid duplicate sends on retries; priority lanes so OTP codes aren't stuck behind marketing blasts; per-user rate limiting/aggregation ("5 people liked your post"); provider quotas; templating & localization; quiet hours.

Web crawler

Crawl billions of pages, politely (robots.txt, per-domain rate limits), prioritizing fresh/important pages, avoiding duplicates and traps, storing content for indexing.

Seed URLs ──► URL Frontier (priority queues by importance + per-host queues enforcing politeness delay; backed by Redis/disk) ──► Fetchers (async I/O, thousands of concurrent connections; DNS cache; robots.txt cache) ──► Content store (blob) ──► Parser/extractor ──► URL filter (normalize, dedupe via Bloom filter / URL-seen DB, domain allowlist) ──► back to Frontier ──► Content dedupe (SimHash / MinHash for near-duplicates) ──► Indexer

Dives: politeness = one connection per host at a time, delay between fetches; frontier partitioned by host hash so a host maps to one fetcher; trap detection (infinite calendars, URL length limits, depth limits); freshness via recrawl schedule based on change frequency; distributed across DCs with consistent-hashed URL ownership; monitor fetch rate, error rates per domain, frontier size.

Distributed cache (design Memcached/Redis cluster)

get/set/delete with sub-ms latency, 10M+ QPS, 100 TB across nodes, tolerate node loss, minimize remapping on topology change.

Client library (or proxy like mcrouter/twemproxy): consistent hashing w/ vnodes → node; connection pooling; local L1 cache for hot keys; request batching (multi-get) Nodes: slab allocator (memcached) / jemalloc (redis), LRU per slab class, single-threaded event loop or multi-threaded workers, no disk Cluster: gossip for membership + failure detection; replicas (warm standby or N copies w/ async replication); hot-key detection & replication; consistent hash ring maintained by clients from a config service

Dives: Meta's mcrouter handles routing, pools, failover (gutter pool for dead nodes), replication to regions, and "lease" semantics against stampedes. Discuss: eviction, TTL, memory fragmentation, big values, network as the bottleneck (10 Gbps ≈ 1.25 GB/s; 1 KB values → ~1M ops/s per NIC), incast congestion from huge multi-gets (many servers reply simultaneously → switch buffer overflow — fix: sliding window on client).

File storage & sync (Dropbox / Google Drive)

Upload/download files up to GBs, sync across devices, versioning, sharing, 500M users × 10 GB.

Client: chunk file into 4 MB blocks → hash each (SHA-256) → ask metadata service which blocks are new → upload only those (dedupe + delta sync) → commit new file version Block service ──► object storage (blocks addressed by hash, replicated/erasure-coded) Metadata service (DB: files, versions, block lists, sharing ACLs; sharded by user/namespace) ──► notification service (long-poll) tells other devices "changed" → they fetch metadata + missing blocks Conflicts: last-writer wins + keep "conflicted copy"; offline queue on client

Dives: content-addressed blocks give dedupe across users; resumable uploads; metadata is the hot path (strong consistency, SQL); blob is the cheap path; CDN for popular shared files; client watches FS with inotify/FSEvents; rate-limiting sync storms.

Video platform (YouTube)

Upload ──► blob (raw) ──► transcode pipeline (queue → workers: multiple resolutions/codecs, split into 2–10s segments, DAG of tasks) ──► CDN origin Playback: manifest (HLS/DASH) → client picks bitrate adaptively → segments from CDN edge (99% hit) ; metadata (title, views) in DB + cache; view counts via async aggregation (not synchronous DB increments)

Dives: transcoding is CPU-heavy and parallel per segment; pre-signed upload URLs straight to blob storage (don't proxy through app servers); CDN cost dominates; popular videos pre-pushed to edge; long-tail served from origin; recommendations are a separate ML system; counts use approximate/batched updates.
