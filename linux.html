Linux & Production Troubleshooting

The PE's daily craft. Interviewers hand you a scenario ("the site is slow", "disk is full", "a host won't boot") and watch how you think. The winning pattern is always the same: observe → hypothesize → test → narrow down → fix → prevent, naming the exact tools and what each number means.

The 60-second triage (memorize; say it out loud in interviews) 
uptime                    # load averages: trend? (1 vs 5 vs 15 min)
dmesg -T | tail           # kernel errors: OOM kills, disk errors, NIC resets
vmstat 1 5                # r (runnable), b (blocked), si/so (swap), us/sy/id/wa (CPU breakdown), cs
mpstat -P ALL 1           # per-CPU: one core pegged? (single-threaded bottleneck / IRQ)
pidstat 1                 # per-process CPU
iostat -xz 1              # per-disk: r/s w/s, await (latency), %util, avgqu-sz
free -m                   # memory: available, swap used, buff/cache
sar -n DEV 1              # NIC throughput, errors/drops
sar -n TCP,ETCP 1         # new connections/s, retransmits (network trouble!)
top / htop                # the overview; sort by CPU, MEM
(Brendan Gregg's "Linux Performance Analysis in 60,000 Milliseconds" — the Netflix checklist.)

Shell & text processing for ops basics

Meta PE coding rounds are often "practical Python/bash": parse a log, aggregate, find top-N. Be fluent.

# top 10 IPs by request count in an access log
awk '{print $1}' access.log | sort | uniq -c | sort -rn | head -10

# 5xx per minute
grep ' 5[0-9][0-9] ' access.log | awk '{print substr($4,2,17)}' | uniq -c

# p99 latency from a column (field 10, ms)
awk '{print $10}' access.log | sort -n | awk '{a[NR]=$1} END{print a[int(NR*0.99)]}'

# find files >1G modified in last day; largest dirs
find / -xdev -type f -size +1G -mtime -1 -exec ls -lh {} \;
du -xh --max-depth=2 / 2>/dev/null | sort -rh | head

# processes in D state and what they wait on
ps -eo pid,stat,wchan:30,cmd | awk '$2 ~ /^D/'

# which process listens on 8080
ss -tlnp 'sport = :8080'

# watch something change
watch -n1 'ss -s; cat /proc/loadavg'

# safe log tail with context
journalctl -u app --since "-15m" | grep -iE 'error|exception' -A3 | less

# replace in-place across files, with backup
sed -i.bak 's/old-host/new-host/g' /etc/app/*.conf

# xargs parallel over hosts
cat hosts | xargs -P 20 -I{} ssh -o ConnectTimeout=3 {} 'uptime'

Know: pipes & redirection (2>&1, &>/dev/null, tee), exit codes ($?, set -euo pipefail), $(), loops, trap, cut/tr/sort/uniq/wc/xargs/awk/sed/grep -E, jq for JSON, ssh -L/-R/-J tunnels, rsync, screen/tmux, nohup.

Incident scenarios, worked end to end PE core

For each: say what you'd check first, what each result would imply, and how you'd prevent recurrence. Practice narrating.

1. "The website is slow." (the open-ended classic)
Scope it: Slow for everyone or some users/regions? All pages or one endpoint? Since when — correlate with deploys/config changes (most incidents are change-induced). Check dashboards: latency p50/p99, error rate, traffic. Is it slow or erroring?
Follow the request path, outside-in: DNS (dig timing), TLS/connect time (curl -w), LB health (backends up? uneven?), app servers (CPU? threads blocked?), downstream (DB latency, cache hit ratio, queue lag), network (retransmits, packet loss via mtr).
On a slow host: 60-second triage. High us → app CPU (profile with perf/py-spy). High sy/si → kernel/network. High wa + await → disk. st → noisy VM neighbor. Swap in/out → memory pressure. Many threads in D → I/O/NFS. Connection pile-up in ss (SYN-RECV, CLOSE-WAIT = app not closing) → backlog/app bug.
Common root causes: cache hit ratio dropped (cache restart / key change) → DB overloaded; slow query after data growth (missing index); GC pauses; connection pool exhaustion; a retry storm; a dependency's latency without timeouts; disk filling → fsync latency; cert/DNS misconfig causing retries.
Mitigate: rollback, scale out, shed load, failover, turn off the feature. Then root-cause, postmortem, add alert on the leading indicator you were missing.
2. "Disk is full on a production host."

df -h (which FS?) → df -i (inodes?) → du -xsh /* | sort -h drilling down → usual suspects: /var/log (unrotated logs, journald — journalctl --disk-usage, --vacuum-size), /tmp, core dumps, docker images/volumes (docker system df), package caches, database binlogs. If du ≪ df: deleted-but-open files → lsof +L1 → truncate via /proc/PID/fd/N (don't just delete). Also: a filesystem mounted over a directory that had data. Immediate relief: truncate (not rm) the biggest log, compress, move. Prevent: logrotate (size-based + compress + copytruncate or reopen signal), disk alerts at 80% with trend ("full in 6h"), separate partitions for /var/log and data, quotas, reserved blocks (ext4 5% root reserve).

3. "A service keeps getting OOM-killed."

dmesg -T | grep -i -A5 oom → which process, its RSS, cgroup limit. Is it a leak (RSS climbs steadily → heap profiling, check for unbounded caches/queues), a legit need (limit too low; set via systemd MemoryMax/k8s resources), a burst (large batch job), or page cache accounting in the cgroup? Check memory.stat anon vs file. Look at Slab in meminfo (kernel memory leak — dentry explosion from tmp files). Mitigate: restart (buys time), raise limit, enable swap for soft landing, reduce workers. Prevent: alert on RSS trend, set oom_score_adj so the right thing dies (protect sshd/agents), load test memory.

4. "Load average is 200 on a 32-core box."

Is it CPU (R) or I/O (D)? vmstat 1: high r + low idle → CPU; high b + high wa → I/O. ps -eo stat,cmd | sort | uniq -c counts states. CPU: top → a fork bomb/runaway script? Too many worker processes configured (e.g., 500 PHP-FPM workers)? Steal time? I/O: iostat -x → which disk; iotop → who; a hung NFS mount (mount, dmesg: nfs: server not responding) makes every process touching it D-state forever. Fix NFS: umount -f -l, use soft,intr mounts for non-critical data.

5. "Can't SSH into a host."

Layered: ping (ICMP may be blocked — not conclusive) → nc -zv host 22 (TCP open?) → if refused: sshd down / wrong port; if timeout: network/firewall/host down → check from another host in the same subnet (is it the host or the path?), console/BMC/IPMI access → on console: is it booted? disk full (sshd can't write)? OOM? Auth failing (ssh -vvv, journalctl -u sshd): keys, permissions on ~/.ssh (700/600), /etc/hosts.deny, PAM, LDAP down, home dir on hung NFS (login hangs!), max sessions. Fleet-wide: config push broke sshd_config (→ sshd -t validation in CI), firewall rule, DNS. Prevent: out-of-band console, canary config changes, never restart sshd without sshd -t and a second session open.

6. "Half the requests to a service fail with connection timeouts."

"Half" smells like one of two backends (or one of two LB nodes / one AZ) is bad. Check LB backend health; hit each backend directly with curl. On the bad one: is it listening (ss -tlnp)? SYN backlog overflow (nstat | grep ListenOverflows → raise somaxconn + app backlog, or app is too slow to accept)? conntrack table full (dmesg: nf_conntrack: table full, dropping packet)? Ephemeral port exhaustion on a client/proxy (many TIME_WAIT — ss -s; fix: keep-alive/connection pooling, tcp_tw_reuse, widen ip_local_port_range)? Half-open firewall/asymmetric routing (tcpdump: SYNs arriving, SYN-ACKs not returning)? DNS returning a dead IP (check all A records)? MTU/blackhole (small requests work, large fail — ping -M do -s 1472).

7. "DNS resolution is intermittently failing."

dig against each configured resolver (/etc/resolv.conf, or resolvectl status); compare authoritative (dig +trace / dig @ns1). UDP packet loss → truncation/retries (check 5 s timeouts in app logs = resolver timeout). Resolver overloaded or rate-limiting; conntrack full on the resolver; negative caching of a transient failure; TTL too low → QPS storm; one bad resolver in the list (glibc tries in order, first one timing out adds 5 s to everything). Mitigate: local caching resolver (systemd-resolved/dnsmasq/unbound) on every host, multiple resolvers, options timeout:1 attempts:2 rotate, app-level DNS caching with sane TTL respect. Note: Java caches DNS forever by default — a notorious problem on failover.

8. "Deploy went out and error rate spiked to 30%."

Roll back first — don't debug in prod with users bleeding. Then: diff the deploy (code, config, dependency versions, schema). Errors in logs (stack traces), new exceptions, changed timeouts, environment variable missing, incompatible API between new and old instances during the rollout (mixed versions), cold caches/JIT warmup under full traffic, a migration locking a table. Prevent: canary with automated analysis, staged rollout, backward-compatible changes, feature flags, pre-prod load test, deploy during low traffic with someone watching.

9. "A host won't boot."

Console (IPMI/serial). Where does it stop? POST/firmware (hardware: RAM, disk missing) → bootloader (GRUB rescue: wrong root UUID after disk swap, corrupt /boot) → kernel panic (bad kernel update, missing initramfs driver, fsck required, root FS corruption) → systemd emergency mode (fstab entry for a missing disk — use nofail; failed mount) → network (DHCP/PXE). Boot an older kernel from GRUB; rd.break/rescue initramfs; chroot from live media. In a datacenter: automated remediation — reimage via PXE if the host doesn't come back in N minutes; hardware ticket if POST fails. A PE answer should mention fleet automation not just manual repair.

10. "A process is using 100% CPU and not responding."

top -H -p PID (which thread?) → perf top -p PID or py-spy top/jstack/gdb -p → stack shows a spin loop, a lock convoy, GC storm, regex backtracking, infinite retry loop. strace -p showing no syscalls = pure user-space compute (or spinlock); a flood of futex = lock contention; EAGAIN loop = broken event-loop logic. Decide: kill and restart (capture a core/dump first for postmortem: gcore), or isolate it with renice/cgroup until you can debug.

11. "Clock drift broke things." (certs invalid, Kerberos failing, logs out of order)

timedatectl, chronyc tracking/sources — is NTP synced? Large offsets, a VM paused and resumed, NTP server unreachable (firewall UDP 123). TLS fails "certificate not yet valid"; Kerberos 5-min skew; distributed systems with LWW lose data. Fix NTP; for big steps restart time-sensitive services. Prevent: monitor offset, multiple NTP sources, chrony makestep on boot.

12. "Filesystem went read-only."

ext4/XFS remount read-only on I/O errors to protect data. dmesg: EXT4-fs error … Remounting filesystem read-only, SCSI/NVMe errors, smartctl for failing disk. Writes fail with EROFS everywhere (logs, DB!). Action: fail over the service off this host, back up what you can, fsck unmounted, replace the disk. Fleet: automated drain + repair workflow triggered by dmesg patterns.

Performance methodology deep dive

  • USE per resource (CPU, memory, disk, NIC, locks): Utilization, Saturation (queue/wait), Errors. Saturation precedes failure.
  • Latency breakdown: where does the time go? Trace one slow request end to end before optimizing anything.
  • Amdahl's law: speeding up a part that's 10% of the time gives ≤ 10%. Measure first.
  • Little's law: concurrency = throughput × latency. 1000 RPS × 0.2 s = 200 in-flight → that's your thread/connection pool size. Queue depth explodes as utilization → 100% (queuing theory: wait time ∝ 1/(1−ρ)) — why running at 90% utilization hurts p99.
  • Flame graphs (perf → stackcollapse → flamegraph.pl): see where CPU goes across the whole stack.
  • Observer effect: strace can slow a process 10–100×; prefer perf/eBPF in production.
  • Tail latency: p99 is dominated by rare events — GC, compaction, page faults, context switches, network retransmits (200 ms RTO minimum!), hedged requests fix it from the client side.

Self-test: Linux rapid fire

What does %wa in top mean, and is high wa always bad?
Time CPUs were idle while at least one I/O was outstanding. It indicates I/O-bound workload; it's "wasted" CPU but may be normal for a storage server. Correlate with iostat await — high await = disk latency problem; high wa with low await = just lots of I/O.
Difference between Requires= and After= in systemd?
Requires is a dependency (if B fails to start, A fails/stops); After is ordering only (A starts after B has started). You usually want both: Requires=B After=B. Wants is a soft dependency.
You see thousands of sockets in CLOSE_WAIT. What does that mean?
The remote side closed (sent FIN) and we ACKed, but our application hasn't called close() on the socket — an application bug (leaking connections). TIME_WAIT, by contrast, is normal on the side that closed first and clears after 2×MSL (60 s).
How do you find which process is writing heavily to disk?
iotop -o or pidstat -d 1; confirm with /proc/PID/io (write_bytes) and lsof -p PID to see which files. BCC biosnoop for per-I/O detail.
What is an inode, and how can a disk be "full" with free space?
Inode = metadata structure for a file (permissions, timestamps, block pointers); fixed number created at mkfs. Millions of tiny files (mail spools, session files, cache dirs) exhaust inodes while bytes remain: df -i shows 100% IUse. Fix: delete the small files; long-term use a FS with dynamic inodes (XFS/btrfs) or pack small files.
Walk me through what strace would show for cat file.txt.
execve("/bin/cat"), brk/mmap for loader & libc, openat(AT_FDCWD, "file.txt", O_RDONLY) = 3, fstat(3), read(3, buf, 131072) = N, write(1, buf, N), read(3) = 0, close(3), close(1), exit_group(0).
How do hard links differ from symlinks in failure behavior?
Hard link: same inode, same filesystem only, can't link directories; deleting one name doesn't affect the other. Symlink: separate inode holding a path; can cross filesystems and point to directories; dangles if the target is removed; permissions are the target's.
What's the first thing you do when paged for a major outage?
Acknowledge, check what changed recently (deploys/config/infra), assess impact & scope, start/join the incident channel, and focus on mitigation (rollback/failover/shed) before root cause. Communicate status at intervals. Debug after users are OK.
