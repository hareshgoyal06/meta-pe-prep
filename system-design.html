System Design, from zero to deep

Read top to bottom. Each chapter starts with the basics and escalates into deep dives. Orange PE angle boxes tell you what a Production Engineering interviewer specifically cares about.

What system design actually is

System design is the art of combining a handful of well-understood building blocks (servers, load balancers, caches, databases, queues) so that a product works correctly, stays fast, stays up, and stays affordable as it grows from 10 users to 1 billion. There are no new blocks to invent in an interview. There are only trade-offs to reason about.

Scalability

Handle more load by adding resources, ideally linearly. "If I double the machines, do I double the throughput?"

Availability

Fraction of time the system answers correctly. Measured in "nines". 99.9% = ~8.7 h down/year.

Reliability

Does it do the right thing, every time, even when parts fail? Includes durability (not losing data).

Latency vs Throughput

Latency = time for one request (p50, p99). Throughput = requests per second. They are different; optimizing one can hurt the other (batching ↑ throughput, ↑ latency).

Consistency

Do all readers see the same data at the same time? Strong vs eventual; the central distributed-systems trade-off.

Maintainability / Operability

Can humans run it? Observability, simplicity, deployability. PEs live here.
PE angleSoftware engineers are asked "design Instagram". PEs are more often asked "design the infrastructure for X" — e.g., a metrics pipeline, a config distribution system, a deployment system, a log aggregator — and then grilled on: what breaks, how you'd know, how you'd debug it, how you'd scale it 10×. Always volunteer failure modes and monitoring without being asked.

The one skill: the "why / what if" ladder

Interviewers climb a ladder: "Why a cache here?" → "What if the cache dies?" → "What if it comes back empty?" → "What if a single key gets 1M QPS?" You win by having a trade-off answer at every rung. Every section below is organized to give you those rungs.

Foundations: how a request travels basics

Everything starts with client–server: a client (browser, phone app, another service) sends a request over a network to a server, which returns a response.

Vocabulary you need

API styles

Resources as URLs, HTTP verbs as actions, JSON bodies. GET /users/42, POST /users, DELETE /users/42. Stateless, cacheable (GET), human-readable, universally supported.

Good for: public APIs, CRUD. Weak at: over/under-fetching, strict typing, high-performance internal calls.

Host: api.example.com
Authorization: Bearer eyJ...

HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: max-age=60
ETag: "a3f9"

{"id":42,"name":"Ada","email":"ada@example.com"}

Status codes to know: 200 OK, 201 Created, 204 No Content, 301/302 redirects, 304 Not Modified, 400 Bad Request, 401 Unauthenticated, 403 Forbidden, 404, 409 Conflict, 429 Too Many Requests, 500, 502 Bad Gateway (upstream dead), 503 Unavailable (overloaded), 504 Gateway Timeout.

Call a remote function like a local one. gRPC = Protocol Buffers (binary, schema'd, compact) over HTTP/2 (multiplexed, streaming). 5–10× smaller payloads and far cheaper parsing than JSON. Code-generated clients in every language. Supports bidirectional streaming.

Good for: internal service-to-service calls (this is what Meta uses internally, via Thrift). Weak at: browsers (needs grpc-web), human debugging.

service UserService {
  rpc GetUser (GetUserRequest) returns (User);
  rpc StreamEvents (Empty) returns (stream Event);
}
message User { int64 id = 1; string name = 2; string email = 3; }

Client specifies exactly the fields it wants in one query; server resolves a graph. Solves over/under-fetching for mobile. Invented at Facebook. Downsides: caching is harder (everything is POST to one endpoint), expensive queries can be abused (need depth/complexity limits), N+1 problem on the server (use DataLoader batching).

For server → client push (chat, notifications, live dashboards):

  • Short polling: client asks every N seconds. Simple, wasteful, latency = N.
  • Long polling: server holds the request open until data exists or timeout. Near-realtime, works everywhere, but a held connection per client.
  • Server-Sent Events: one-way HTTP stream from server. Simple, auto-reconnect, text only.
  • WebSockets: full-duplex persistent TCP connection after an HTTP upgrade. Best for chat/games. Cost: stateful connections — LB must support them, and a server with 1M connections holds 1M sockets (memory, file descriptors!).

Stateless vs stateful services — the most important design choice

Stateless prefer

Server keeps nothing between requests; all state lives in a DB/cache. Any server can handle any request → trivial horizontal scaling, trivial failover, safe to kill & redeploy. Session data → cookie/JWT or Redis.

Stateful

Server holds client state (sessions, WebSocket connections, in-memory shard). Needs sticky routing, careful failover, and data migration on scale-out. Sometimes unavoidable (databases, caches, WebSocket gateways) — isolate it into a dedicated tier.

RulePush state to the edges (client) or the bottom (storage tier). Keep the middle (application tier) stateless. Nearly every scaling trick depends on this.

Back-of-the-envelope estimation basics

Interviewers want to see you size the problem before designing. The goal is order of magnitude, not precision. Round aggressively.

Users → requests. DAU × actions per user per day = requests/day. Divide by 10⁵ (≈86,400) to get QPS. Peak ≈ 2–5× average.
Read/write ratio. Most systems are read-heavy (10:1 to 100:1). Writes drive storage & DB design; reads drive caching.
Storage. Writes/day × object size × days retained × replication factor (usually 3).
Bandwidth. QPS × payload size. Compare to NIC (1 Gbps ≈ 125 MB/s; 10 Gbps ≈ 1.25 GB/s).
Memory for cache. 80/20 rule: cache 20% of daily read volume to serve ~80% of reads.
Machines. Peak QPS ÷ per-machine capacity (+ headroom, + N+1 redundancy, + one failure domain).

Interactive estimator

Say it like this"100M DAU × 20 requests ≈ 2B requests/day ≈ 20k QPS average, call it 60k peak. 10:1 reads so ~6k writes/s. 500 B per write → ~250 GB/day new data → ~450 TB over 5 years with 3× replication. That won't fit on one box → we need sharding. 60k reads/s → a few dozen app servers behind an LB, and a cache tier because most reads are repeated."

Scaling: vertical, horizontal, and load balancing basics

Vertical scaling (scale up)

Bigger machine: more CPU, RAM, faster disks. Pros: zero code changes, no distributed-systems problems. Cons: hard ceiling, exponentially pricier, single point of failure, downtime to upgrade. Always the first step; never the last.

Horizontal scaling (scale out)

More machines, commodity hardware. Pros: near-unlimited, fault-tolerant (one dies, others continue), cheap. Cons: requires statelessness or partitioning, introduces network failures, consistency problems, operational complexity. This is what the rest of this page is about.

Load balancers

A load balancer (LB) sits in front of a pool of identical servers, spreading requests and hiding failures. It is the component that makes horizontal scaling possible.

Load balancing simulator

Kill a server: health checks remove it from rotation and traffic flows to survivors. With IP hash, note which clients move. Try weighted RR with S1 w=3.

Layer 4 vs Layer 7 deep dive

L4 (transport)

Looks only at IP + TCP/UDP port. Forwards packets (NAT or Direct Server Return). Extremely fast (millions of connections), protocol-agnostic, cheap. Cannot route by URL or inspect content. Examples: Linux IPVS, AWS NLB, Maglev, Katran (Meta's XDP-based L4 LB).

L7 (application)

Terminates TCP+TLS, parses HTTP. Routes by path/host/header/cookie, does TLS offload, compression, auth, rate-limiting, retries, WebSocket upgrade, observability. Slower & more CPU, but smart. Examples: Nginx, HAProxy, Envoy, AWS ALB, Proxygen (Meta).

Typical production stack: DNS/anycast → L4 LB tier (stateless, ECMP from routers, consistent hashing of connections) → L7 proxy tier → services. The L4 tier makes the L7 tier horizontally scalable; the L7 tier makes services smart.

Health checks & failure handling

  • Active: LB probes /health every N seconds; mark unhealthy after K failures, healthy after M successes (hysteresis prevents flapping).
  • Passive: watch real traffic; eject on 5xx/timeouts (outlier detection).
  • Shallow vs deep health checks: "process is up" vs "I can reach my DB". Deep checks can cause cascading removal when a shared dependency hiccups — a classic outage. Prefer shallow for LB, deep for alerting.
  • Connection draining: on deploy, stop sending new requests but let in-flight ones finish.
Who balances the load balancer?LBs come in pairs (active-passive with a floating VIP via VRRP/keepalived) or as a stateless horizontally-scaled tier using ECMP + consistent hashing (Maglev/Katran). DNS or anycast spreads traffic across LB clusters and regions.

Global traffic: DNS, GeoDNS, anycast, CDN edge

  • DNS round robin: return multiple A records; crude, clients cache, no health awareness.
  • GeoDNS: resolver location → nearest datacenter's IP. Latency-based routing. TTL (60 s) bounds failover time.
  • Anycast: same IP announced from many PoPs via BGP; the internet routes to the nearest. Instant failover, DDoS absorption. Used for DNS roots, CDNs, Meta's edge.
  • Edge PoPs: terminate TLS close to the user (short RTT for handshake), keep warm long-lived connections back to the datacenter. Huge latency win.

Caching basics

A cache stores a copy of expensive-to-compute or slow-to-fetch data in a fast place (memory) so repeat requests are cheap. It is the single highest-leverage performance tool: memory access is ~100 ns, SSD ~100 µs, a DB query over the network ~1–10 ms.

Cache-aside: the app checks the cache first and falls back to the DB on a miss.

Caching strategies (read & write paths)

App reads cache → miss → read DB → write cache. Writes go to DB and invalidate (delete) the cache key. Most common. Cache only holds what's requested. Risk: stale data between DB write and invalidation; race where a slow reader writes an old value after the invalidation (fix: short TTL, or "lease"/CAS as in Meta's memcache paper).

Cache itself loads from DB on miss (the cache library has the loader). Same semantics as cache-aside, cleaner code, cache becomes a dependency.

Every write goes to cache and DB synchronously. Cache is always fresh; write latency = max of both. Pairs well with read-through. Cache may fill with data never read.

Write to cache only; flush to DB asynchronously (batched). Extremely fast writes, absorbs bursts. Risk: data loss if cache dies before flush. Used in CPU caches, OS page cache, some counters/analytics.

Writes bypass cache, go to DB; cache fills on read. Avoids polluting cache with write-once data (logs). First read after write is a miss.

Eviction policies

LRU simulator

Capacity:

Access A,B,C,D then A — A moves to MRU. Access E — B (least recently used) is evicted. Try a scan A,B,C,D,E,A,B,C,D,E at capacity 4 and watch the 0% hit rate: this is why scans poison LRU caches.

  • LRU (least recently used): doubly-linked list + hash map, O(1). Default almost everywhere. Weak against scans.
  • LFU: evict least frequently used. Better for stable popularity; slow to adapt; needs decay.
  • FIFO, Random: simple, surprisingly OK in some workloads.
  • TTL: expire after time; bounds staleness. Redis combines TTL + approximated LRU/LFU sampling.
  • ARC / W-TinyLFU: adaptive hybrids (Caffeine) resistant to scans and one-hit wonders.

Cache problems you must know deep dive

Cache invalidation & staleness

"There are only two hard things in CS: cache invalidation and naming things." Options: TTL (simple, bounded staleness), explicit delete-on-write (precise, race-prone), versioned keys (user:42:v7 — never invalidate, just stop referencing), event-driven invalidation via a change-data-capture stream (Meta's approach with Wormhole/TAO). Rule: delete, don't update, the cache on write — updating risks reordered writes leaving a stale value permanently.

Cache stampede / thundering herd

A hot key expires → thousands of concurrent requests miss simultaneously → all hit the DB → DB falls over. Fixes: (1) request coalescing / single-flight: only one request recomputes, others wait; (2) leases (Memcache): cache hands a token to the first misser; (3) probabilistic early refresh: refresh slightly before expiry with increasing probability; (4) stale-while-revalidate: serve stale, refresh in background; (5) jittered TTLs so keys don't expire together.

Cold start / cache warming

A new or restarted cache has 0% hit rate → full load hits the DB. Fixes: pre-warm from a snapshot or replaying recent keys, gradual traffic ramp (slow-start in the LB), keep DB provisioned to survive a cache outage (or accept degraded mode with load shedding).

Hot keys

A celebrity's profile or a viral post gets 1M QPS on one key → one cache shard saturates (network or CPU). Fixes: replicate the hot key across N shards (key#1..N, read random), local in-process cache for the hottest items (L1 cache in app), detect hot keys via sampling and auto-promote.

Big keys & memory fragmentation

A 50 MB value blocks the Redis single thread for ms, hurts p99. Split big values, compress, or store in blob storage with a pointer in cache. Watch used_memory vs RSS for fragmentation.

Consistency between cache replicas / regions

Multi-region caches see writes at different times. Meta: writes go to the primary region's DB; MySQL replication stream carries invalidations ("mcsqueal") to remote regions' caches; remote-region readers after a write can be routed to the primary briefly ("remote marker"). Read the 2013 "Scaling Memcache at Facebook" paper — it is practically a PE interview script.

CDN (Content Delivery Network)

Hundreds of edge PoPs cache static (and increasingly dynamic) content near users. Push CDN: you upload content to the CDN proactively (good for rarely-changing, large files). Pull CDN: edge fetches from origin on first miss, then caches per TTL (simpler, standard). Cache key = URL (+ selected headers). Invalidate by purging or, better, by fingerprinting filenames (app.3f9a1c.js) with immutable long TTLs. CDNs also absorb DDoS, terminate TLS near users, and do image resizing/video segment delivery.

Databases: the storage layer basics

A database durably stores data and lets you query it. The two big families, and the honest truth: start with a relational DB (Postgres/MySQL) unless you have a specific reason not to.

Relational / SQL

Tables with fixed schemas, rows, foreign keys. Strong ACID transactions, rich queries (JOINs, aggregations), mature tooling. Scales reads via replicas easily; scales writes via sharding with effort. MySQL, PostgreSQL. Meta runs one of the largest MySQL fleets in the world (with its own storage engine, MyRocks).

NoSQL

Umbrella for everything else; each trades some SQL power for scale or flexibility:
• Key-value (Redis, DynamoDB, RocksDB): get/put by key. Fastest, simplest.
• Wide-column (Cassandra, HBase, Bigtable): rows with dynamic columns, partitioned by key, sorted within partition. Huge write throughput.
• Document (MongoDB, Couchbase): JSON docs, flexible schema, nested data.
• Graph (Neo4j, TAO at Meta): nodes & edges, traversal queries (friends-of-friends).
• Time-series (Prometheus, InfluxDB, Gorilla/Beringei at Meta): append-mostly, time-bucketed, compressed.
• Search (Elasticsearch, Solr): inverted indexes for text.

How a database stores and finds data: indexes

Without an index, finding a row = scanning the whole table (O(n)). An index is a separate sorted structure mapping a column's values → row locations.

  • B+ tree (MySQL InnoDB, Postgres): balanced, sorted, O(log n), great for point lookups and range queries (WHERE ts BETWEEN). Updates in place → random I/O.
  • Hash index: O(1) equality only; no ranges. Memory stores (Redis), some engines.
  • LSM tree (RocksDB, Cassandra, HBase, MyRocks): writes go to an in-memory memtable + sequential write-ahead log; flushed as immutable sorted files (SSTables); background compaction merges them. Sequential I/O → very high write throughput and better compression; reads may check multiple levels (mitigated by Bloom filters). Write-optimized vs B-tree's read-optimized.
  • Inverted index: term → list of documents. Full-text search.
  • Composite index on (a, b): usable for WHERE a=… and WHERE a=… AND b=…, but NOT WHERE b=… alone (leftmost-prefix rule).
  • Covering index: index contains all queried columns → no table lookup.
Indexes aren't freeEach index slows every write (must update N trees), consumes storage, and the DB can only use so many per query. Index what you filter/sort/join on; never index blindly.

Transactions and ACID

Atomicity

All or nothing. Transfer $100: debit AND credit, or neither. Implemented via undo logs / WAL.

Consistency

Constraints (unique, FK, checks) hold before and after. (Different meaning from CAP's "consistency"!)

Isolation

Concurrent transactions don't see each other's partial work. Levels: Read Uncommitted → Read Committed → Repeatable Read (MySQL default) → Serializable. Implemented via MVCC and/or locks.

Durability

Once committed, survives crashes. Write-ahead log fsync'd to disk before ack. (fsync latency ≈ 1–10 ms on SSD → why DBs batch commits.)

MVCC (multi-version concurrency control): each write creates a new version tagged with a transaction ID; readers see the snapshot as of their start → readers never block writers. Old versions are garbage-collected (Postgres VACUUM, InnoDB purge). This is how Postgres/MySQL/Oracle do it.

Optimistic vs pessimistic locking: pessimistic = lock rows up front (safe, contention). Optimistic = read a version number, write with WHERE version = v, retry on conflict (great for low contention).

Replication basics

Replication = keeping copies of the same data on multiple machines. Why: (1) availability — a replica takes over if the primary dies; (2) read scaling — spread reads across replicas; (3) latency — put copies near users; (4) durability — data survives disk loss.

Single-leader (primary–replica)

  • Synchronous replication: leader waits for replica ack before confirming the write. No data loss on failover; but write latency = slowest replica, and one dead replica blocks writes. Usually semi-synchronous: wait for 1 of N replicas.
  • Asynchronous: leader confirms immediately, streams changes later. Fast; but replication lag (ms to seconds, or minutes under load) → stale reads, and the most recent writes are lost if the leader dies.

Problems caused by replication lag deep dive

Read-your-own-writes

User updates profile, refreshes, sees the old one (read hit a lagging replica). Fixes: read from the leader for a few seconds after a write (track last-write timestamp per user, in a cookie or session); route reads of "own" data to the leader; replicas report their position and clients wait until caught up.

Monotonic reads

User sees a comment, refreshes, it disappears (second read hit a more-lagged replica). Fix: pin each user to one replica (hash user id → replica).

Consistent prefix / causality

Observer sees the answer before the question because they replicated through different partitions. Fix: write causally related data to the same partition; or causal-consistency tracking (version vectors).

Failover: when the leader dies

Detect: heartbeats time out (e.g., 10–30 s). Too short → false positives under load spikes; too long → longer outage.
Elect: choose the most up-to-date replica (consensus — see Raft — or an orchestrator like Orchestrator/MHA, or ZooKeeper).
Reconfigure: clients and other replicas point to the new leader (update DNS/VIP/service discovery/proxy).
Dangers: split brain — old leader comes back thinking it's still leader; two leaders accept writes → divergence. Needs fencing (STONITH: "shoot the other node in the head", or epoch/fencing tokens). Lost writes: async replicas lacked the old leader's last transactions → discard them (data loss) or reconcile. The GitHub 2018 outage is the canonical case study: a 43-second network blip caused a cross-DC failover with divergent writes and a 24-hour degraded recovery.

Multi-leader

Each datacenter has its own leader accepting writes; leaders replicate asynchronously to each other. Pros: local write latency, DC-level fault tolerance, offline clients (calendar apps, CRDT docs). Cons: write conflicts — the same row changed in two places. Resolution: last-writer-wins (LWW, loses data silently), per-field merge, application-level merge, CRDTs (conflict-free replicated data types — counters, sets, text that merge mathematically). Avoid unless you really need it; when needed, partition so each record has a "home" region.

Leaderless replication & quorums (Dynamo-style)

No leader. Client (or coordinator) writes to all N replicas, waits for W acks; reads from all N, waits for R responses, takes the newest version. If W + R > N, every read set overlaps every write set → at least one replica has the latest value → strong-ish consistency. Cassandra, Riak, DynamoDB, Voldemort.

Quorum calculator

  • Sloppy quorum & hinted handoff: if home replicas are down, write to any N reachable nodes, who "hand off" the data when the home nodes return. Availability over consistency.
  • Read repair: on read, if replicas disagree, write the newest version back to stale ones.
  • Anti-entropy: background process comparing Merkle trees between replicas to find & fix differences efficiently.
  • Version vectors / vector clocks: detect concurrent writes (siblings) rather than silently losing one. Clients must merge.

Partitioning (sharding) basics

Replication copies all data to every node — it doesn't help when the data (or write load) is too big for one machine. Partitioning splits the dataset so each node holds a subset (a shard). Usually combined: each shard is itself replicated.

Partitioning strategies

Shard by key ranges: A–F, G–M, N–Z; or by time: 2024-01, 2024-02. Pro: range queries hit one shard; sorted scans are efficient. Con: hot spots — all today's writes go to the "current" shard; celebrity names cluster. Used by HBase, Bigtable, Spanner (with automatic splitting).

shard = hash(key) mod N (or consistent hashing). Pro: uniform distribution, no hot spots from key skew. Con: range queries must hit all shards (scatter-gather); adjacent keys are scattered. Cassandra uses hash for the partition key but sorts within the partition by clustering columns — best of both for "all messages for chat X ordered by time".

A separate service maps key → shard (e.g., user_id → shard in a lookup table or ZooKeeper). Pro: total flexibility, can move individual tenants, handle hot tenants specially. Con: lookup service is a SPOF & extra hop (cache it heavily). Used by Vitess, many multi-tenant SaaS, Meta's shard manager.

Shard by region (EU users in EU) for latency and data-residency law; or by entity (all of a company's data on one shard). Good locality; uneven shard sizes.

The rebalancing problem & consistent hashing deep dive

With hash(key) mod N, going from N=3 to N=4 nodes remaps ~75% of keys → massive data movement / cache miss storm. Consistent hashing places nodes and keys on a ring; each key belongs to the first node clockwise. Adding a node only steals keys from its one neighbor (~1/N of keys move).

Consistent hashing ring

Dots on the inner ring are keys; colored arcs show which node owns which range. Add a node and read the log: only a small fraction of keys move. Then slide virtual nodes up: with 1 vnode the arcs are badly uneven (one node may own 50% of keys); with 50 vnodes each node owns ≈ equal share, and removing a node spreads its keys across all survivors instead of dumping them on one neighbor.

Virtual nodes (vnodes): each physical server gets 100–200 points on the ring → even load, heterogeneous weights (bigger server → more vnodes), and smooth redistribution on failure. Used by Cassandra, DynamoDB, Riak, Memcache clients (ketama), Discord, and the L4 load balancer Maglev uses a related lookup-table scheme.

Alternatives: fixed number of many small partitions (e.g., 1024) assigned to nodes via a map (Kafka, Elasticsearch, Redis Cluster's 16384 slots) — simpler to reason about, just move whole partitions. Jump consistent hash and rendezvous (HRW) hashing are stateless alternatives.

Hard problems with sharding

Hot shards / celebrity problem

Even with hashing, one key can be hot (Justin Bieber's followers list). Fixes: split hot keys with a suffix (key#0..k) and fan out; dedicated handling for "whale" entities; app-level caching of hot items; for write-hot keys, aggregate in memory then flush.

Cross-shard queries & joins

"Find all posts by users in city X" must query every shard (scatter-gather) → latency = slowest shard, load ×N. Fixes: denormalize (store what you need together), secondary-index service (local index per shard = scatter on read; global index partitioned by indexed term = scatter on write), async-materialized views, or a separate search/analytics system fed by CDC.

Cross-shard transactions

Moving money between users on different shards. Options: two-phase commit (2PC: coordinator asks all "prepare?", then "commit" — blocking if coordinator dies; slow); sagas (sequence of local transactions with compensating actions on failure — eventually consistent); choose shard keys so related entities co-locate (shard by account, not by transaction); use a DB with distributed transactions built in (Spanner, CockroachDB, TiDB — at a latency cost).

Unique IDs across shards

Auto-increment doesn't work across shards. Options: UUIDv4 (random 128-bit; bad B-tree locality), Snowflake IDs (64-bit: 41-bit timestamp + 10-bit machine id + 12-bit sequence → time-sortable, 4096/ms/machine; Twitter, Instagram's variant includes shard id), DB ticket server (Flickr: one MySQL that only hands out IDs — SPOF unless two with odd/even), ULID/KSUID (sortable, string-friendly).

Resharding live

Double shards with zero downtime: (1) start dual-writing to old and new layout; (2) backfill historical data; (3) verify (checksums); (4) switch reads; (5) stop writing to old. Use a directory-based shard map so the switch is a config flip. Pre-split into many logical shards (e.g., 4096) mapped onto few physical nodes so "resharding" is just moving logical shards.

Consistency, CAP, and the real trade-offs basics

Once data lives on more than one machine, you face the question: when a client reads, which version do they see? "Consistency" in distributed systems means "all clients see the same data at the same time" (not the ACID meaning).

CAP, interactively

CAP theorem (Brewer): when a network Partition happens, a distributed system must choose between Consistency (every read returns the latest write or an error) and Availability (every request gets a non-error response). Partitions are not optional in real networks, so the choice is really C-vs-A during failures.

PACELC extends it: if Partition → A or C; Else (normal operation) → Latency or Consistency. Even without failures, synchronous replication (consistency) costs latency. DynamoDB/Cassandra: PA/EL. Spanner/ZooKeeper: PC/EC. MySQL async replication: PA/EL-ish.

Interview trapDon't say "we pick AP" and move on. Say which operations need which guarantee: "Likes count can be eventually consistent; account balance and username uniqueness need strong consistency, so those paths go through the leader with synchronous replication."

Idempotency: the practical consistency tool

Networks fail; clients retry; the server may receive the same request twice. An idempotent operation produces the same result no matter how many times it runs. PUT /balance {value: 50} is idempotent; POST /deduct {amount: 50} is not. Make non-idempotent operations idempotent with an idempotency key: client generates a unique request ID; server stores processed IDs (with TTL) and returns the stored response on duplicates. Stripe's API is the canonical example. Essential for payments, queue consumers (at-least-once delivery), and any retry logic.

Consensus & coordination deep dive

Many problems reduce to getting several machines to agree on one value: who is the leader? what is the next log entry? who holds the lock? That's consensus. It's hard because machines crash, messages get delayed, and clocks are unreliable — you can't distinguish "slow" from "dead".

Raft leader election simulator

Green = leader, yellow = candidate, dark = follower. The arc around each node is its randomized election timer, reset by every heartbeat (blue dots). Kill the leader → heartbeats stop → the first follower to time out becomes a candidate, increments the term, requests votes (yellow), wins with a majority (green dots), and starts sending heartbeats. Crash a majority → nobody can win → cluster is unavailable but never inconsistent.

Raft, in plain terms

Roles: leader, follower, candidate. One leader per term (a monotonically increasing number acting as a logical clock).
Election: followers expect heartbeats. Timeout (randomized 150–300 ms to avoid ties) → become candidate, term++, vote for self, request votes. Majority → leader. Nodes vote for at most one candidate per term, and only one whose log is at least as up-to-date.
Log replication: client writes go to the leader; leader appends to its log and sends AppendEntries to followers; once a majority acknowledge, the entry is committed and applied to the state machine; followers learn commit index from later heartbeats.
Safety: a committed entry is never lost because any future leader must have a majority's votes, and a majority includes at least one node with that entry. Majorities always overlap — that's the whole trick.
Cost: every write = 1 RTT to a majority. 5 nodes tolerate 2 failures; 3 tolerate 1. Use odd counts. Don't run 100 nodes in a Raft group — use it for small metadata, not for data.

Paxos is the older, equivalent-in-power protocol (Multi-Paxos ≈ Raft); Raft was designed to be understandable. Zab is ZooKeeper's variant. All three: majority quorums, leader-based, linearizable log.

Coordination services: ZooKeeper / etcd / Chubby

Small, strongly consistent, highly available key-value stores built on consensus. You don't put your data there — you put coordination metadata there:

  • Leader election: everyone tries to create an ephemeral node /leader; whoever succeeds is leader; if it dies, its session expires, the node vanishes, and watchers race again.
  • Service discovery / membership: each instance registers an ephemeral node; clients watch the directory.
  • Distributed locks: ephemeral sequential nodes; lowest sequence holds the lock; watch the one before you (avoids herd).
  • Configuration: config in znodes; clients get watch notifications on change. Kubernetes stores its entire cluster state in etcd.
  • Shard assignment: which node owns which partition (Kafka used ZK until KRaft).

Distributed locks are dangerous

Time & clocks

  • Wall clocks (NTP) drift and jump; never use them to order events across machines. "Last-write-wins by timestamp" silently loses data.
  • Monotonic clocks for measuring durations on one machine.
  • Logical clocks: Lamport timestamps (total order consistent with causality), vector clocks (detect concurrency: A→B, B→A, or concurrent).
  • TrueTime (Google Spanner): GPS+atomic clocks give a bounded uncertainty interval; commit waits out the uncertainty → external consistency across the globe. Hardware, not magic.
  • Hybrid logical clocks (CockroachDB): wall clock + logical counter.

Asynchronous processing & message queues basics

Not every piece of work needs to happen while the user waits. A message queue lets a producer hand off work and move on; consumers process it later at their own pace. This is the primary tool for decoupling, absorbing bursts, and fan-out.

Patterns

  • Work queue (point-to-point): each message consumed by exactly one worker. Competing consumers scale horizontally. (RabbitMQ queues, SQS.)
  • Pub/sub (fan-out): each message delivered to every subscriber group. (Kafka topics with consumer groups, SNS, Redis pub/sub.)
  • Event sourcing / log: the queue is the source of truth; consumers rebuild state by replaying. (Kafka with long retention.)
  • CDC (change data capture): tail the DB's binlog into a stream to update caches, search indexes, warehouses. (Debezium, Meta's Wormhole.)
  • Outbox pattern: write the DB row and an "outbox" row in one transaction; a relay publishes outbox rows → no dual-write inconsistency.

Kafka vs RabbitMQ (log vs broker) deep dive

Kafka (distributed log)

Topics split into partitions; each partition is an append-only, ordered log on disk, replicated (leader + ISR followers). Consumers track their own offset — messages aren't deleted on read (retention by time/size). Ordering guaranteed within a partition (choose partition key = user_id for per-user order). Throughput: millions msg/s via sequential I/O, zero-copy sendfile, batching. Consumer group: each partition → exactly one consumer in the group → max parallelism = #partitions. Replay possible. Great for streams, event sourcing, log pipelines.

RabbitMQ / SQS (smart broker)

Broker pushes messages to consumers, tracks acks, deletes on ack, supports routing (exchanges, topics, headers), priorities, per-message TTL, delayed delivery. Lower throughput, richer semantics, simpler for task queues. No replay. SQS: fully managed, nearly infinite scale, at-least-once, visibility timeout, FIFO variant.

Delivery semantics

GuaranteeHowCost
At-most-onceFire and forget; ack before processingMessages may be lost. Metrics, logs where loss is OK.

Operating queues

  • Backpressure: when consumers can't keep up, queue depth grows (lag). Alert on consumer lag. Options: scale consumers, shed load, bound the queue and reject producers (fail fast), or drop low-priority messages.
  • Poison messages & DLQ: a message that always fails blocks retries forever. After N attempts, move to a dead-letter queue for inspection; alert on DLQ size.
  • Ordering vs parallelism: strict global ordering = 1 partition = 1 consumer. Pick the narrowest key that needs ordering.
  • Retries with backoff via delay queues / retry topics (retry-1m, retry-10m, retry-1h).
  • Hot partitions: a partition key with skew (one giant customer) saturates one broker/consumer. Same fixes as hot shards.

Resilience patterns: designing for failure PE core

At scale, something is always broken. Disks fail at ~2–4%/year; with 10,000 disks that's one per day. The goal is not to prevent failure but to contain it so users don't notice.

Timeouts, retries, and backoff

The #1 cause of cascading failuresService A calls B with no timeout. B slows down. A's threads all block waiting on B. A runs out of threads and stops serving its other endpoints. A's callers pile up. The whole site goes down because one dependency got slow. Every network call needs a timeout.
  • Timeouts: set from the caller's p99 + margin; propagate deadlines (caller passes "you have 200 ms left") so downstream doesn't waste work.
  • Retries: only for transient errors (timeouts, 503, connection reset), only for idempotent ops, with a budget (e.g., retries ≤ 10% of requests). Retrying a saturated service makes it worse: retry storms amplify load 2–3×.
  • Exponential backoff + jitter: wait 100 ms, 200, 400, 800… capped, with randomness so clients don't synchronize.

Without jitter, 1000 clients that failed at the same moment all retry at the same moment — a synchronized wave. With jitter the retries are spread uniformly.

Circuit breaker

Stop hammering a failing dependency; return a fallback immediately; probe occasionally to recover. Gives the dependency room to heal.

Rate limiting & load shedding

Token bucket rate limiter

Each request takes one token; tokens refill at a steady rate. Bursts up to the bucket size are allowed; sustained rate is capped at the refill rate. Auto traffic at 5 rps with refill 2/s → ~60% rejected once the bucket drains.

AlgorithmBehaviorNotes
Token bucketAllows bursts up to capacity, average = refill rateMost common (AWS, Stripe). 2 numbers per key — tiny memory.
Leaky bucketRequests queue and drain at constant rateSmooths output; adds latency; used in network shaping.
Fixed windowCount per minuteSimple; 2× burst at window edges (end of minute + start of next).
Sliding window logStore timestamps, count those within last N secExact; memory grows with rate.
Sliding window counterWeighted blend of current and previous fixed windowsGood approximation, O(1) memory. Cloudflare's choice.

Distributed rate limiting: counters in Redis (INCR + EXPIRE, or Lua for atomic token bucket); accept slight over-admission by syncing local counters periodically; or rate-limit at the gateway where there are few nodes. Return 429 with Retry-After.

Load shedding is rate limiting by the server for self-protection: when CPU/queue depth/latency crosses a threshold, reject the cheapest-to-reject requests first (low priority, unauthenticated, retries). Prefer failing 10% of requests fast over failing 100% slowly. Meta's "Adaptive concurrency / criticality-based shedding" is a frequent PE topic.

Bulkheads, isolation, and blast radius

  • Bulkheads: separate thread pools / connection pools / instances per dependency or per customer, so one misbehaving tenant can't exhaust shared resources.
  • Cell-based architecture: partition the whole stack into independent cells (each with its own LB, services, DBs) serving a slice of users. A bad deploy or failure affects one cell (one-N-th of users). Used by AWS, Slack, Meta's regions.
  • Failure domains: rack → row → datacenter → region. Spread replicas across domains; never put all 3 replicas in the same rack (one top-of-rack switch failure = outage).
  • Graceful degradation: when recommendations are down, show the chronological feed. When search is down, show cached results. Define degraded modes up front.

Cascading failures: the full catalogue deep dive

Overload → slowness → retries → more overload (the death spiral)

Server at 100% CPU gets slower → clients time out and retry → load doubles → everything times out. The system can stay down even after the trigger is removed (metastable failure). Fixes: load shedding, retry budgets, circuit breakers, and the ability to drop all traffic and ramp back up slowly.

Thundering herd on recovery

Service comes back; every client reconnects at once; cache is cold; it falls over again. Fixes: jittered reconnects, slow-start traffic ramp at the LB, cache warming, connection rate limits.

Capacity loss from one failure (the N−1 problem)

3 servers at 70% each; one dies; remaining two must take 105% → both die. Provision so losing a failure domain leaves you under 100%. "What's your headroom?" is a classic PE question.

Shared dependency outage

Everything depends on auth / config / DNS / the service-discovery system → that dependency is the whole site's SPOF. Harden those few systems extremely, make clients cache their last good answer, and make startup not depend on them (static fallback). The 2021 Facebook outage: a config push withdrew BGP routes to the DNS servers → DNS down → everything down, including internal tools and door badges.

Bad deploy

Most outages are caused by changes. Fixes: canary (1% of hosts), progressive rollout by region, automatic rollback on SLO regression, feature flags (decouple deploy from release), config changes treated as code with the same rollout discipline.

Service architecture: monolith, microservices, and the plumbing basics

Monolith

One deployable. Simple dev, debug, deploy; in-process calls are free and transactional. Scales fine for a long time (Meta's web tier is a giant PHP/Hack monolith!). Problems: team coupling, one bad change takes down everything, can't scale components independently, long builds.

Microservices

Many small services over the network, each owned by a team, with its own DB. Independent deploy and scale, tech freedom, fault isolation (if done right). Costs: network latency & failures everywhere, distributed transactions, observability needs (tracing), operational burden ×N, versioned APIs. Don't start with microservices. Split when team size or scaling needs demand it.

Supporting infrastructure

  • API gateway: single entry point handling auth, rate limiting, routing, TLS, request logging, protocol translation (REST → gRPC). (Kong, Envoy, AWS API Gateway.)
  • Service discovery: how does A find B's current IPs? Client-side (query a registry like Consul/etcd/ZooKeeper, then LB locally) vs server-side (DNS or an LB in front). Health checks evict dead instances. Kubernetes Services do this via DNS + kube-proxy.
  • Service mesh: a sidecar proxy (Envoy) next to each service handles mTLS, retries, timeouts, circuit breaking, metrics, tracing — uniformly, outside app code. (Istio, Linkerd; Meta uses a library approach — ServiceRouter.)
  • Configuration management: centralized, versioned config with gradual rollout and instant rollback; clients subscribe for changes. Config errors cause as many outages as code — treat with the same care.
  • Containers & orchestration: packaging (Docker) + scheduling/placement/healing/scaling (Kubernetes; Meta's Twine/Tupperware). The scheduler is a bin-packing + constraint solver: spread replicas across failure domains, respect CPU/mem requests, reschedule on node death.

Storage systems at scale deep dive

Object / blob storage

Billions of immutable objects (photos, videos, backups) addressed by key, accessed via HTTP. Flat namespace, no in-place edits, massive scale, cheap. Design: a metadata service (key → location, sharded DB) + storage nodes holding bytes + replication or erasure coding. Writes go to several nodes; reads via any. Meta's Haystack packs many small photos into large append-only files to avoid per-file filesystem metadata overhead (one disk seek per photo instead of three); f4 stores "warm" photos with erasure coding for lower replication cost.

Erasure coding (Reed-Solomon): split data into k chunks + m parity chunks; any k of k+m reconstruct the data. RS(10,4): 1.4× storage overhead tolerating 4 failures, vs 3× for triple replication. Cost: reconstruction reads k chunks (slow, network-heavy) → use for cold data; replicate hot data.

Distributed file systems (GFS / HDFS / Tectonic)

Files split into large chunks (64–256 MB), each replicated 3× across chunkservers. A master/NameNode holds the namespace and chunk locations in memory (metadata only — the bottleneck; HDFS federation and Tectonic shard it). Clients ask the master for locations, then read/write chunkservers directly. Optimized for large sequential reads and appends, not small random writes. Rack-aware placement: 2 replicas in one rack, 1 in another.

Search indexes

Inverted index: term → sorted posting list of doc IDs (+ positions). Query "cats AND dogs" = intersect two posting lists. Sharded by document; each query scatter-gathers across shards and merges top-k. Indexes built offline in batches or near-realtime via segments (Lucene). Relevance via TF-IDF/BM25 then ML re-ranking.

Data pipelines

Batch (MapReduce/Spark on a data lake, hourly/daily): high throughput, high latency, easy reprocessing. Stream (Kafka + Flink/Spark Streaming): seconds latency, windowing, exactly-once via checkpoints; harder. Lambda architecture: both, merged at query time. Kappa: stream only, replay for batch. ETL: ingest → clean → store columnar (Parquet/ORC) → query (Presto/Trino, Hive, Spark SQL).

Observability, SLOs & operating systems in production PE core

You cannot run what you cannot see. PE interviews heavily weight this. For every design, be ready to answer: "how would you know it's broken, and how would you find out why?"

The three pillars

Metrics

Numeric time-series: counters (requests_total), gauges (queue_depth), histograms (latency buckets → p50/p95/p99). Cheap, aggregatable, alertable. Prometheus/Graphite/ODS (Meta). Cardinality (label combinations) is the cost — never put user IDs in labels.

Logs

Discrete events with context. Structured (JSON) → searchable. Expensive at scale (sample, tier, retain briefly). ELK, Splunk, Scribe/Scuba (Meta). Essential for "why did request X fail?"

Traces

A request's path across services: span tree with timings. Propagate a trace ID in headers. Shows where latency goes in a microservice call graph. Jaeger, Zipkin, OpenTelemetry, Canopy (Meta). Sample (1–10%) to control volume.

What to measure: the four golden signals (Google SRE)

  1. Latency — distribution, not average; separate success vs error latency. p99 matters: at 100 calls per page, 63% of users hit a p99.
  2. Traffic — RPS, bandwidth, active connections.
  3. Errors — rate, by type (5xx, timeouts, wrong answers).
  4. Saturation — how full: CPU, memory, disk I/O, queue depth, connection pool usage. Predicts imminent failure.

USE method (Brendan Gregg) for resources: Utilization, Saturation, Errors — for every CPU, disk, NIC, memory. RED method for services: Rate, Errors, Duration.

SLIs, SLOs, SLAs and error budgets

Availability calculator

  • SLI (indicator): a measured ratio — "fraction of requests served under 300 ms with a 2xx".
  • SLO (objective): the target — "99.9% over a 30-day window". Internal; drives engineering decisions.
  • SLA (agreement): the contract with customers with penalties. Always looser than the SLO.
  • Error budget = 1 − SLO. At 99.9%, you may be "bad" for 43 min/month. If the budget is healthy → ship faster; if burned → freeze features, work on reliability. This is how SRE resolves dev-vs-ops tension.
  • Burn-rate alerts: alert when the budget is being consumed X× faster than sustainable (e.g., 14.4× over 1 h and 6× over 6 h) — far better than static "error rate > 1%" thresholds.

Alerting philosophy

  • Page on symptoms (users see errors/latency), not causes (CPU is high). Causes become dashboards.
  • Every page must be actionable and urgent. Otherwise: ticket, not page. Alert fatigue kills on-call.
  • Link every alert to a runbook: what it means, how to check, how to mitigate.
  • Alert on absence of data (the monitoring itself died) and on saturation trends (disk full in 4 h).

Incident response & postmortems

Detect (alert or report) → Triage severity → Declare an incident, assign an Incident Commander (coordinates, doesn't debug), a comms lead, and ops leads.
Mitigate first, root-cause later. Roll back the last change (most outages are change-induced). Fail over. Shed load. Disable the feature flag. Restore service, then investigate.
Communicate on a status page / channel at fixed intervals even if nothing changed.
Blameless postmortem: timeline, impact (users, duration, SLO burn), root cause(s) using "5 whys", contributing factors, what went well, action items with owners. Blameless → people tell the truth → systems improve. Focus on systemic fixes (guardrails) not "be more careful".

Capacity planning

Forecast demand (growth trend + seasonality + launches) → translate to resources (QPS per core, GB per user) → provision with headroom for peak, N+1/N+2 for failure domains, and lead time for hardware (months). Load-test to find the real per-host capacity rather than guessing. Track utilization vs. forecast monthly. Know the difference between provisioned, used, and needed-to-survive-a-region-loss.

Security essentials basics

  • Authentication (who are you) vs authorization (what may you do). Sessions (server-side, revocable) vs JWT (stateless, signed, hard to revoke → short expiry + refresh tokens). OAuth2/OIDC for delegated login. mTLS between services.
  • Passwords: never store plaintext; salt + slow hash (bcrypt/argon2). Hashing ≠ encryption.
  • TLS everywhere; terminate at the edge; re-encrypt internally in zero-trust networks. Certificates expire — the most common self-inflicted outage; automate renewal and monitor expiry.
  • Secrets management: no secrets in code/config repos; use a vault with rotation and audit.
  • Input validation, parameterized queries (SQL injection), output encoding (XSS), CSRF tokens, CORS.
  • DDoS: absorb at the edge (anycast, CDN), SYN cookies, rate limits, prioritize authenticated traffic, scrubbing centers.
  • Least privilege, network segmentation, audit logs, defense in depth.
  • Encryption at rest for disks/backups; key management (KMS) separate from data.

Self-test: system design rapid fire

Your DB is at 90% CPU from reads. First three things you'd do?
1) Find the slow/hot queries (slow log, EXPLAIN) and add indexes or fix N+1 patterns. 2) Add a cache (cache-aside, Redis) for hot reads. 3) Add read replicas and route reads to them (accepting lag; handle read-your-writes). Only then consider sharding.
Why is consistent hashing better than hash mod N?
Adding/removing a node remaps only ~1/N of keys (just the neighbor's range) instead of nearly all keys, avoiding cache-miss storms and massive data movement. Virtual nodes fix load imbalance and spread a dead node's load across all others.
What's the difference between availability and durability?
Availability: can I get an answer right now. Durability: once acknowledged, the data will never be lost. S3 is designed for 99.999999999% (11 nines) durability but 99.99% availability — you might not be able to read it right now, but it isn't gone.
A client got a timeout on a POST /payments. Should it retry?
Only if the operation is idempotent. The server may have processed it. Use an idempotency key: the client sends the same key on retry; the server detects the duplicate and returns the original result instead of charging twice.
Why W + R > N gives consistency, and why it's not perfectly linearizable in practice?
Overlap guarantees at least one replica in the read set has the latest write. But: sloppy quorums, concurrent writes with clock-based LWW, partially failed writes (succeeded on 1 of W), and reads racing with in-flight writes can still return stale/inconsistent results. Dynamo-style systems are "mostly" consistent at W+R>N, not linearizable.
Explain a cache stampede and two fixes.
Popular key expires → many simultaneous misses → DB overload. Fixes: request coalescing/leases (only one recomputes, others wait or get stale), probabilistic early expiration, stale-while-revalidate, jittered TTLs.
Kafka: how do you get ordering AND parallelism?
Ordering is per partition. Choose a partition key that is the smallest unit needing order (user_id, not global). Parallelism = number of partitions; each consumer in a group owns some partitions. Increasing partitions later changes key→partition mapping (breaks ordering across the boundary) so over-provision partitions up front.
What's a fencing token and why does a distributed lock need one?
A monotonically increasing number issued with each lock grant. The protected resource rejects writes with a token lower than the highest seen. Prevents a client that paused (GC, network) past its lease expiry from clobbering writes made by the next lock holder.
Why page on symptoms rather than causes?
Causes are many and noisy (high CPU may be fine); symptoms (error rate, latency SLO burn) are what users feel and are exactly the things worth waking someone for. Cause-based signals belong on dashboards for diagnosis.
Three servers at 70% utilization — are you safe to lose one?
No. Total work = 210% of one server; two survivors would need 105% each. Safe N+1 means each of 3 must run at ≤ 66%. For N+2 (lose two) ≤ 33%. This is why fleets look "underutilized".
Give an example where eventual consistency is fine and one where it is not.
Fine: like counts, view counts, feed ordering, profile picture propagation. Not fine: account balance, inventory for the last item, username uniqueness, access revocation (removing someone's permission must be seen immediately).
How does a circuit breaker differ from a retry with backoff?
Retry/backoff is per-request: keep trying, slower. A circuit breaker is per-dependency state: after enough failures, stop sending requests entirely (fail fast with fallback) and only probe periodically. It protects the failing dependency from load and protects you from waiting on it.
